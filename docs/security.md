# 安全设计

先说前提：这是一个**单用户、暴露在公网、语义等价于远程命令执行**的服务。DSH 会在服务器上执行命令，任何进到界面的人就拿到了那台机器的执行能力。下面说的是，设计如何在承认这个前提的情况下把风险收窄。

## 威胁模型

| 威胁 | 场景 | 对策 |
| --- | --- | --- |
| 公网扫描 | 攻击者扫到网关端口上的 TLS 服务 | 没有网关口令越不过第二层；DSH 侧还有第三层 |
| 口令爆破 | 反复尝试网关口令 | bcrypt 校验成本 + 中继侧 fail2ban 封 IP（只统计带 `Www-Authenticate` 的口令失败） |
| 中间人 | 链路被旁听或篡改 | TLS；内网到中继的 SSH 固定主机密钥 |
| 访问地址泄漏 | 收藏的地址落到别人手里 | 该地址不含任何秘密，单独无效 |
| Cookie 失窃 | 浏览器侧 Cookie 被读走 | `HttpOnly` + `SameSite=Strict` + `Secure` + 权威绑定（换权威即失效） |
| 中继上其他端口的服务 | 别的服务读到或写入同一个 Cookie | 中继只开网关一个 HTTP 端口（见下文） |
| 中继主机被入侵 | 中继被攻破 | 中继上没有 DSH 凭据，但隧道上的明文流量可被读到——这是本架构的固有代价，见下 |
| 伪造 Host 打本机 | 本机上的恶意页面用 DNS rebinding 打 `127.0.0.1` | DSH 既有的围栏；本设计只增加一个必需权威，不扩大到通配 |
| 局域网直连 | 同网段设备直连 DSH | DSH 仍只听 loopback；插件从不请求 `0.0.0.0` |
| 引导过程泄漏口令 | 口令出现在命令行或日志里 | 唯一的用户口令只经 stdin 交给中继上的 `caddy hash-password`；日志与记录里只出现"已设置"。管理登录走密钥，不存在管理口令 |

### 中继主机被入侵要如实说明

中继的 `authorized_keys` 上有一条允许内网主机建立反向转发的公钥。中继被攻破时，攻击者可以监听隧道终点上的明文 HTTP（TLS 已在 Caddy 终止）并读走经过的 Cookie，也可以直接向该端口发请求并把 Host 设成声明的权威。

这一点不能靠插件消除，只能靠"中继上只跑 `sshd` 与 Caddy、及时打补丁、安全组只开必要端口"来压低。它也是把中继当作**需要自己维护的机器**、而不是"外部服务"的理由。

## 分层防御

```
第一层  TLS 校验            阻止被动旁听与中间人
第二层  网关口令            阻止无口令访问（bcrypt + 网关会话 Cookie）
第三层  DSH 会话 Cookie     阻止无 Cookie 的 RPC；换权威即失效
第四层  DSH Host/Origin 围栏 阻止跨站与 DNS rebinding
```

四层互相独立，任一层失效不连带其他层。第一、二层在中继主机，第三、四层在内网主机。

**为什么第二层是必需的。** DSH 自身的认证是单操作者的：一个启动令牌、一个长期 Cookie，没有多用户、没有吊销列表、没有频率限制。把它直接挂到公网，等于把一个能远程执行命令的界面挂到公网。

**DSH 不给 Cookie 加 `Secure`，由中继补上。** DSH 下发的是 `Max-Age; Path=/; Expires; HttpOnly; SameSite=Strict`，没有 `Secure`。缺这一位时，同一个权威上的任何一次明文请求都会把 Cookie 送出去。插件不修改 DSH 源码，所以这一位由中继在响应经过时补上；部署第 13 步的自检盯着它。

**中继上只有一个 HTTP 端口，这是 Cookie 的要求而不只是收缩攻击面。** Cookie 不提供端口隔离（RFC 6265 第 8.5 节）：同一台主机上另一个端口上的服务既读得到也写得到同一个 Cookie。所以"权威只以 HTTPS 提供服务"和"中继上不存在第二个 HTTP 服务端口"是同一件事的两半，插件在这两条上都不提供配置项。

这条要求需要你和插件共同兑现：apt 装出的发行版默认 Caddyfile 末尾有一个 `:80` 静态站点，插件按约不碰托管块之外的内容。删掉它的步骤见 [排障与维护](troubleshooting.md#中继上出现了多余的监听端口)。

## 网关会话与口令

第二层由 Caddy 的口令校验（bcrypt）与它下发的一个会话 Cookie 共同构成，会话有效期 12 小时——这就是"每次进入输一次口令"的节奏。

这里有一条必须成立的不变量：**会话 Cookie 只在认证成功之后下发，未认证请求绝不能拿到它**。Caddy 的指令执行顺序由它自己的指令表决定而不是书写顺序，站点模板因此把这一段放进按书写顺序执行的 `route` 里，口令校验拒绝时短路。改模板时要连带重跑"未认证请求不返回 `Set-Cookie`"这条自检——这是整份配置里最容易在改动中被破坏、又最不显眼的一条。

口令弹窗里的账号名固定为 `me`，但**弹窗不会提示它**：Safari 与 Chrome 都不再显示 realm，因为服务器控制的一段文字不该出现在受信任的浏览器 UI 里。所以这个固定的公开名字不是秘密，也不带来安全收益；口令才是秘密，落盘的只有它的 bcrypt 哈希，明文不落中继磁盘。

## 证书与 CA

中继用 Caddy 内置的本地 CA 为 IP 权威签发证书：根证书 10 年，站点证书 90 天，Caddy 自己负责续签。

**这是这条通路上唯一需要你拍板的选项**，两条路：

- **安装 CA 根证书（推荐）。** 根证书只有公钥，可以公开分发。它不经过公网 HTTP：引导已经把它取回本机，你在设置页状态区点「下载根证书」拿到文件，再经本机复制、隔空投送、聊天软件等不依赖 TLS 信任的渠道送到设备。装之前与设置页显示的指纹核对。iOS 上还要到 设置 ▸ 通用 ▸ 关于本机 ▸ 证书信任设置 里手动开启完全信任。
- **不安装**，每次访问手动点过浏览器的证书警告。这时 TLS 仍然加密流量，但**没有身份验证**：你无法察觉中间人，攻击者只要能劫持到中继 IP 的流量就能读走 Cookie 与口令。

这是明确要接受的风险，不是"等价但更省事"的选项。把这一条写在这里，是为了让"不装 CA"是一个被看见的决定。

IP 字面量无法使用 HSTS（RFC 6797 明确排除 IP 字面量），所以无域名的方案里没有"靠浏览器强制升级"这条退路。

## 凭据落在哪

| 材料 | 位置 | 权限 |
| --- | --- | --- |
| 部署参数（含明文网关口令） | profile 的 `cordis.patch.yml` | `0600`；不在 git 仓库里。管理登录走密钥，插件不存管理口令 |
| 运行记录（含网关会话密钥） | `$DSH_HOME/dsh-web-relay/record.json` | `0600`，目录 `0700`。会话密钥不经过记录接口出去 |
| 隧道专用私钥 | `$DSH_HOME/dsh-web-relay/ssh/relay_ed25519` | `0600`，父目录 `0700` |
| 中继主机公钥记录 | `$DSH_HOME/dsh-web-relay/ssh/known_hosts` | `0600`，只含中继一条 |
| 中继 CA 根证书副本 | `$DSH_HOME/dsh-web-relay/ca/root.crt` | `0644`（公开信息） |
| DSH 会话签名密钥 | `$DSH_HOME/.credentials.yaml` | 由 DSH 管理 |

**中继上唯一的加密凭据是网关口令的 bcrypt 哈希**（写在 Caddyfile 里）。明文在引导结束后不存在于中继磁盘上。

## 吊销与轮换

| 目标 | 动作 | 影响 |
| --- | --- | --- |
| 换掉网关口令 | 在设置页重填口令并部署 | 口令重新哈希，同时重置网关会话密钥，所有设备下次进入要重输口令 |
| 作废全部 DSH 会话 | 删除 `$DSH_HOME/.credentials.yaml` 里的 `client-connection/browser-session` 记录并重启 | 全部旧 Cookie 校验失败；设备下次打开访问地址时会自动被带回换票点 |
| 收回隧道权限 | 从中继的 `/etc/dsh-web-relay/authorized_keys` 删掉那一行并重载 `sshd` | 中继不再接受该反向转发，隧道下次重连即失败 |

**重启 profile 不会吊销 Cookie**：签名密钥是复用的持久化凭据。重启也不会让公网入口重新可用——隧道只在一次部署里建立。

换权威（改地址或网关端口）会让所有旧 Cookie 立刻失效，因为 Cookie 的名字与签名负载都绑定权威。这是设计使然，不是缺陷。

## 远程页面的功能边界

DSH 的客户端在非 loopback 页面上把设置持久化降级为内存，一批功能因此在远程设备上不可用：

| 类别 | 远程是否可用 | 说明 |
| --- | --- | --- |
| 模型设置、通用设置的导入/导出/重置 | 不可用 | 依赖设置持久化 |
| 权限的**默认**预设 | 不可用 | 只是"对未来会话的默认值" |
| **本插件的设置页** | 不可用 | 远程页面读不到插件的设置命名空间，这个标签页根本不注册 |
| 新建/切换工作区、新建会话、对话、文件上传 | 可用 | 会话面不受影响 |
| 全部 `/api` 调用与 WebSocket | 可用 | |

插件不能改掉这条限制，只能把它变成流程的一部分：**首次配置与每一次部署都在服务器本机完成**，远程只需打开访问地址并输入网关口令。

## 已知限制

**目录选择器在远程会选到原生后端。** 远程请求目录选择时，原生选择器会在服务器那块屏幕上弹出。这是部署选择，插件不做检测也不改它。

**隧道断开对攻击者无信息。** 浏览器看到的是中继上可读的一段"无法连接内网主机"提示。

**无域名带来三项代价**：客户端要信任私建 CA、无法使用 HSTS、不能监听 80/443。有了备案域名之后切到 ACME 自动证书，三项一起消失。

**`dsh web` 的绑定校验不被绕过。** DSH 的启动校验拒绝监听 `0.0.0.0`；插件从不尝试放宽它。

## 明确不做

| 项 | 为什么不做 |
| --- | --- |
| 域名与 ACME 自动证书 | 需要备案域名；有域名后换掉中继的站点地址与证书来源即可，不需要改插件 |
| 中继侧状态页 | 免登录地把"隧道是否连通"暴露在公网，本身是一个需要额外设计的信息面；设置页与部署自检已经覆盖同一个问题 |
| 中继侧 TOTP | 需要在中继上多跑一个服务，破坏"中继只有 sshd 与 Caddy"这条简化 |
| 多中继与故障切换 | 单用户场景收益低，而代价是权威集合、访问地址、自检都要处理"哪一个可用" |
| 中继上的第二个 HTTP 端口 | Cookie 不按端口隔离，多一个端口就多一条读到会话 Cookie 的路 |
| 桌面端 | 桌面端走 IPC、不开端口，没有需要转发的东西 |
| 逐设备令牌与吊销 | 浏览器侧只能退化成"口令换 Cookie"，在单用户场景下并不比现在更强；全量吊销仍可用轮换 DSH 会话密钥实现 |
| URL 里携带入口凭据 | 入口凭据一旦进了 URL，就会跟着收藏夹、历史与设备同步走；口令由浏览器口令框承载，只经过请求头 |
| 远程改配置 | 这是 DSH 对非 loopback 页面的既定行为，任何绕过它的做法都要在插件里另建一套配置面 |
| 中继侧定时清理监听残留 | 那需要在中继上装一个常驻单元；主机侧的转发前预检在需要时做同一件事，且不留下常驻物 |

## 部署完成后必须成立的前提

下面每一条都要成立；任何一条不成立，安全性就低于本设计的假设。

1. 中继上只跑 `sshd` 与 Caddy，没有第三个对外服务，也没有第二个 HTTP 端口。
2. 中继的安全组只开放网关端口（以及你自己管理用的 SSH 来源）。
3. TLS 证书被客户端真实校验，而不是"永久忽略证书错误"。
4. 认证成功的响应里每条 `set-cookie` 都带 `Secure`；认证失败的响应里没有 `set-cookie`。
5. `authorized_keys` 上用于隧道的公钥带 `restrict,port-forwarding,permitlisten`，端口与插件的中继端口一致。
6. `sshd` 的 `GatewayPorts` 为 `no`，转发端点不绑到公网接口。
7. 权威、Caddy 站点地址、DSH 围栏的受信项三者一致。
8. 中继侧访问日志不记录查询串里的秘密。
9. 你已经决定是否安装 CA 根证书，并知道不装时没有身份验证。
10. 中继上 `ss` 可用，且管理账号能免密 `sudo`（或本身就是 `root`）。

第 4、5、6、7 条由部署的自检盯着；其余几条需要你在中继上确认，核对方式见 [排障与维护](troubleshooting.md)。
